# Project brand voice card

Use this when the user asks to build, reuse, or update a voice card, or when an existing card for the current project's brand would inform the writing. The card is plain Markdown. The project determines where it lives, including in a project note if the user chose that location. For a single brand and no existing convention, propose `brand-voice.md` in the project root. In multi-brand or multi-language projects, name the brand/register and keep each card or clearly scoped section separate.

## Find and apply the right card

1. Use an explicitly supplied card first, then a card referenced in the current project's instructions or brief, then the project's default `brand-voice.md` if it exists. Limit discovery to the named project and explicitly supplied locations. Verify the brand and scope before using examples. A fixture, generated suggestion, or neighboring brand card is an example of form unless the user identifies it as applicable.
2. Apply the current brief's voice instructions to this task. Use the matching card to fill the remaining choices. If a one-off instruction differs from the saved voice, follow it for this deliverable and keep the saved guidance. If the project/card identity is ambiguous, use the explicit voice in the brief and ask only if the unresolved choice materially affects the writing.
3. Convert the cues into actual editorial decisions: register, rhythm, point of view, intensity, vocabulary, and any constructions to avoid. Use approved examples for voice evidence and write fresh lines around today's footage and payoff. Treat saved language about products, results, offers, or customer stories as material to verify in the current brief. Voice fit and evidence fit are separate checks.
4. Without a matching card, use the brief or provided samples. Label an inferred voice as provisional when the deliverable calls for a rationale. One sample can support a tentative cue. Apply it without claiming a durable preference.

## Create or update only when requested

Draft from the user's supplied or approved samples. Separate **confirmed** preferences, **proposed** inferences, and **unresolved** feedback. Mark a rejected line and its reason only when the user actually rejected it, and preserve which project or register it applied to. If the user asks to save an explicit durable preference, update the selected project card and preserve unrelated notes. Ask for the destination only if the project is ambiguous. A request to use a card or make a one-off edit authorizes reading and application. A request to save or update authorizes the project write. Keep private samples and brand notes inside that project's chosen location.

## Copyable Markdown starter

```markdown
# Brand voice — [brand or project]

Scope: [brand, language/register, channels or exceptions]
Basis: [approved samples or user guidance; identify source]

## Confirmed
- [Observable choice and when to use it]

## Approved examples
- “[Actual approved line]” — [why it fits, if known]

## Avoid
- “[Actual rejected line or confirmed construction]” — [reason and scope]

## Provisional
- [Inference to test, or unresolved preference]
```

For example, “calm” can become “begin with the object, use short observations, and let the demonstrable change carry the surprise.” Attach that guidance to actual accepted language before marking it confirmed. For video, apply the approved register only to shots the [footage-first workflow](footage-first.md) can support.
